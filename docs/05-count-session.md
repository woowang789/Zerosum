# 실사와 판매 가능 수량

## 실사 세션

실사는 사람이 몇십 분에 걸쳐 수량을 세는 작업이다. 그 사이 출고가 끼어들면 작업자가 센 수량과 시스템 수량이 서로 다른 순간을 가리키게 되어, 멀쩡한 재고에 가짜 조정이 들어간다. 이를 막기 위해 실사를 `count_session`으로 관리하고, 진행 중인 세션을 `location.count_session_id`에 표시한다. 제출, 정정, 중단 요청은 [멱등성](04-write-path.md#멱등성)의 멱등 키를 받는다. 키는 세션 id에서 파생하고(`count:submit:{세션id}`) 세션 id는 재사용되지 않으므로 그 일은 평생 한 번만 일어난다. 시작만 멱등 키를 받지 않는다 — 아래 "시작" 참고.

| 상태 | 의미 | 로케이션 표시 |
|---|---|---|
| OPEN | 수량을 세는 중 | 설정 |
| REVIEW | 제출했으나 허용 오차를 넘는 차이가 있어 검토 중 | 유지 |
| CONFIRMED | 차이가 없었거나 정정 거래까지 끝남 | 해제 |
| ABANDONED | 정정 없이 중단 (재실사 등) | 해제 |

**시작.** 로케이션 행을 잠그고, 이미 열린 실사가 있으면 그 세션을 돌려주고, 없으면 세션 생성과 로케이션 표시를 한 트랜잭션에서 한다.

```sql
-- 동시 시작을 직렬화한다. 진행 중인 포스팅의 FOR SHARE가 끝날 때까지 여기서 기다린다
SELECT count_session_id FROM location WHERE id = :locationId FOR UPDATE;
-- 널이 아니면 그 세션 id를 그대로 반환하고 끝낸다 (재시도의 재생)

-- 부분 유니크 인덱스가 같은 로케이션의 동시 실사를 막는다
INSERT INTO count_session (location_id, started_by)
VALUES (:locationId, :userId)
RETURNING id;

UPDATE location
SET count_session_id = :sessionId
WHERE id = :locationId AND count_session_id IS NULL;   -- 잠금 아래이므로 영향 행 수는 항상 1
```

**시작에 멱등 키를 쓰지 않는 이유.** 멱등 키는 업무 식별자로 만든다. `receipt:{발주라인}:{입고차수}`가 유일한 것은 그 입고가 평생 한 번 일어나기 때문이다. 그런데 "이 로케이션을 실사한다"는 **반복되는 일**이다. 순환 실사는 정기적으로 돈다. 그래서 `count:start:{창고}:{로케이션}` 같은 키를 쓰면 두 번째 실사가 첫 번째의 재생이 되어, 한 로케이션을 평생 한 번만 실사할 수 있게 된다 — `idempotency_record`에는 해제가 없기 때문이다(I6).

재시도의 재생은 상태가 대신한다. "이 로케이션에 열린 실사가 있다"는 이미 `location.count_session_id`가 들고 있고, 유일성은 부분 유니크 인덱스 `uq_count_session_active`(I10)가 DB에서 강제한다. 위의 `FOR UPDATE`가 그 표시를 잠금 아래에서 읽으므로, 같은 요청이 두 번 들어오든 두 사용자가 동시에 시작하든 둘 다 같은 세션 id를 받는다. 멱등 기록은 같은 사실을 한 겹 더 들고 있었을 뿐이다.

이 `FOR UPDATE`는 로케이션 행에 배타 잠금을 걸어 포스팅이 쥔 FOR SHARE와 충돌한다. 그래서 진행 중인 포스팅이 끝난 뒤에야 표시되고, 이후 포스팅은 커밋된 표시를 읽고 거절된다. 뒤따르는 UPDATE가 어차피 같은 강도로 잠그던 행이므로 잠금 순서(location → stock_balance)는 달라지지 않고, 획득 시점만 같은 트랜잭션 안에서 앞당겨진다.

포스팅이 FOR KEY SHARE가 아니라 FOR SHARE를 쓰는 이유도 이 경계에 있다. 외래키 검사용인 FOR KEY SHARE는 키가 아닌 컬럼을 바꾸는 UPDATE(FOR NO KEY UPDATE 강도)와 충돌하지 않는다. 시작은 위처럼 명시적 `FOR UPDATE`로 잠그니 FOR KEY SHARE와도 충돌하겠지만, 아래 정정·중단이 표시를 지우는 `UPDATE location SET count_session_id = NULL`은 그냥 UPDATE다 — 여기서 FOR KEY SHARE는 경계를 만들지 못한다.

**제출.** 세션 행을 FOR UPDATE로 잠그고 OPEN인지 확인한 뒤, 라인별 실재고를 `system_qty`로 `count_result`에 기록한다. 표시가 커밋된 뒤로는 이 로케이션의 실재고를 바꾸는 포스팅이 모두 거절되므로 이 값은 실사 시작 시점의 값과 같다. 모든 라인의 차이가 허용 오차 이내면 같은 트랜잭션에서 아래 정정 절차로 끝내고, 하나라도 넘으면 세션을 REVIEW로 바꾸고 `inventory_issue`를 만든다. 금액은 범위 밖이므로 허용 오차도 수량 기준으로 정한다.

허용 오차는 코드에 박지 않고 설정으로 뺀다. 실제 차이 분포를 보고 조정할 값이기 때문이다. 출발값은 "차이 1개 이하이면서 5% 이하"이며, 두 조건이 AND라는 점에 주의해야 한다. 이 값이면 재고가 20개 미만인 로케이션에서는 1개 차이도 5% 조건에 걸려 REVIEW로 간다. 소량 다품종 창고라면 REVIEW가 쏟아질 수 있으므로, 운영 데이터를 본 뒤 OR로 완화하거나 SKU 등급별로 나누는 것을 검토한다. 처음에는 보수적인 쪽이 낫다 — 가짜 정정보다 사람 검토가 안전하고, REVIEW로 쌓인 차이 데이터가 순환 실사 우선순위 모델의 학습 라벨이 된다.

**정정.** 순서가 핵심이다. 세션 행을 id 순서로 잠그고, 로케이션 행도 id 순서로 잠가 표시를 먼저 지운 뒤, 같은 트랜잭션에서 정정 거래를 포스팅하고 세션을 CONFIRMED로 바꾼다. 표시를 지운 UPDATE가 로케이션 행을 배타 잠금으로 쥐고 있어 커밋 전에는 다른 포스팅이 끼어들 수 없고, 포스팅 서비스는 자기 트랜잭션에서 지운 표시를 보므로 실사용 예외 규칙이 따로 필요 없다. 정정이 실패하면(예: 실재고가 할당량보다 적어져 CHECK 위반) 표시 삭제까지 함께 롤백되어 로케이션은 계속 잠겨 있고, 할당 해제를 먼저 처리한 뒤 다시 정정한다. 여러 로케이션을 한 번에 바로잡는 AI 제안(예: 분실·발견 조정 2건 대신 이동 1건)은 `RESOLVE_COUNT` 커맨드로 들어와 같은 절차로 실행된다.

**중단과 방치.** 재실사가 필요하거나 작업이 취소되면 정정 없이 ABANDONED로 바꾸고 표시를 지운다. OPEN이나 REVIEW로 오래 남은 세션은 해당 로케이션의 출고를 계속 막으므로 알림 대상이다. OPEN이 오래가면 버려진 실사이고, REVIEW가 오래가면 처리되지 않은 차이다.

**DB 잠금이 아니라 컬럼인 이유.** 시작과 제출은 서로 다른 HTTP 요청이고 그 사이가 몇십 분이다. 트랜잭션을 그만큼 열어두면 커넥션을 점유하고, VACUUM이 오래된 행을 치우지 못해 테이블이 부풀며, 서버가 재시작되면 잠금이 사라진다. 그래서 짧은 행 잠금은 시작 순간의 경계만 줄 세우고, 긴 잠금 상태는 데이터로 남긴다. 표시를 세션 테이블이 아니라 location 행에 두는 것도 포스팅의 FOR SHARE와 충돌시키기 위해서다.

## 판매 가능 수량

실사 중인 로케이션의 재고는 지금 출고할 수 없고, 실사 결과에 따라 줄어들 수도 있다. 게다가 순환 실사는 오차 가능성이 높은 로케이션부터 고르므로([기능별 데이터 매핑](07-ai-integration.md#기능별-데이터-매핑)의 7번 기능), 실사 중인 재고는 창고에서 가장 믿기 어려운 재고이기도 하다. 그래서 기본 정책은 실사 중 수량을 채널 노출 수량과 할당 후보에서 모두 빼는 것이다. 코어는 정책을 강제하지 않고 두 숫자를 나눠 제공하며, 채널 연동(범위 밖)이 이 뷰를 읽어 SKU별 정책을 적용한다.

```sql
CREATE VIEW v_sellable_stock AS
SELECT b.warehouse_id,
       b.sku_id,
       COALESCE(SUM(b.on_hand_qty - b.allocated_qty)
                FILTER (WHERE loc.count_session_id IS NULL), 0)     AS sellable_qty,
       COALESCE(SUM(b.on_hand_qty - b.allocated_qty)
                FILTER (WHERE loc.count_session_id IS NOT NULL), 0) AS in_count_qty
FROM stock_balance b
JOIN location loc ON loc.id = b.location_id AND loc.is_sellable
GROUP BY b.warehouse_id, b.sku_id;
```

**노출과 할당 정책은 반드시 짝을 맞춘다.** 채널에 `in_count_qty`까지 노출하면서 할당은 실사 중 로케이션을 제외하면, 채널에서 팔린 주문이 할당 단계에서 재고 부족으로 실패한다. 반대로 할당만 허용하고 노출은 빼면 판매 기회만 잃는다. 그래서 할당 커맨드의 `allowInCount`는 채널 노출 정책과 같은 값을 따른다.

**`allowInCount`에는 기본값을 두지 않는다.** 기본값이 있으면 호출자가 의식하지 않고 넘어가고, 노출 정책만 바뀐 날 짝이 어긋나 주문이 조용히 실패한다. 필수 파라미터로 두면 채널 연동을 만들 때 반드시 한 번 결정하게 된다.

**예외가 필요한 SKU.** 재고 대부분이 한 로케이션에 몰린 SKU는 실사 동안 채널에서 품절로 보이고, 채널 재고가 주기적으로 반영되는 구조라면 반영 주기보다 짧은 실사는 수량을 흔들기만 한다. 이런 SKU는 실사 중 수량을 노출과 할당에 포함하고 출고만 실사 종료 뒤로 미루거나(실사 결과 수량이 줄면 할당 해제와 주문 지연을 감수), 실사를 주문이 적은 시간대에 배치하고 실사 우선순위 점수에 판매 영향을 반영한다.

어느 정책이든 계산은 뷰에서 일어나고 실재고와 원장은 그대로이므로, 이 결정은 정합이 아니라 판매 정책의 문제다. 할당은 location을 잠그지 않아서 실사 시작과 거의 동시에 들어온 할당이 막 표시된 로케이션에 붙을 수 있는데, 이는 실사 시작 직전에 들어온 할당과 같은 상태라 따로 막지 않고 제출·정정 단계에서 기존 할당과 똑같이 처리한다.
