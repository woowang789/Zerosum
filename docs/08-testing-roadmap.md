# 테스트 전략과 구현 순서

## 테스트 전략

스키마 자체는 구현에 앞서 이미 한 번 검증했다. [스키마 검증](09-schema-validation.md)에 유스케이스 83건과 그 결과가 정리되어 있고, 실행 스크립트는 `db/`에 있다. 그 검증의 자산은 두 가지다 — **유스케이스 시나리오와 기대 결과**, 그리고 그것을 돌린 PL/pgSQL 하네스. 시나리오는 아래 Testcontainers 테스트로 그대로 옮기고, 하네스는 남겨둔다. 스키마만 바꿨을 때(컬럼 추가, 제약 변경) Java 컴파일 없이 몇 초 만에 전부 다시 돌려볼 수 있어서, 마이그레이션을 고칠 때 가장 먼저 도는 검사가 된다.

정합 테스트는 Testcontainers로 띄운 실제 PostgreSQL에서 돌린다. H2는 행 잠금 동작이 다르고 지연 제약 트리거와 PL/pgSQL을 지원하지 않아서, 여기서 통과해도 정합성의 증거가 되지 못한다.

| 시나리오 | 기대 결과 |
|---|---|
| 가용 50개인 SKU에 200개 스레드가 1개씩 동시 할당 | 성공 정확히 50건, `allocated_qty` = 50, 정합 검증 0건 |
| A→B 이동과 B→A 이동을 동시에 1,000회 | 데드락 0건, 두 로케이션 합계 불변 |
| 같은 멱등 키로 출고를 동시에 10회 | 거래 1건, 나머지 9회는 같은 결과 반환 |
| 같은 멱등 키에 다른 수량 | 409 |
| 이미 출고된 입고를 역분개 | 음수 방지로 실패 |
| 합계가 0이 아닌 원장을 직접 INSERT | 커밋 시 트리거 오류 |
| 실사 시작과 출고가 동시에 경합 | 출고는 실사 시작 전에 커밋되거나 거절됨, 제출 시 `system_qty`가 원장 합계와 일치 |
| 같은 로케이션에 실사 시작을 동시에 2회 | 세션 1개만 생성 |
| REVIEW 상태 로케이션에서 출고 | 거절 |
| 실재고가 할당량보다 적어지는 정정 | 표시 삭제까지 롤백, 로케이션은 계속 잠김 |
| 실사 중 로케이션이 있는 SKU 할당 (`allowInCount = false`) | 실사 중 로케이션에는 할당되지 않고 `sellable_qty`에서도 제외 |
| 같은 제안을 동시에 5회 승인 | 거래 1건, EXECUTED 1회 |
| 제안 후 재고가 크게 변한 뒤 승인 | 원장 기록 없음, 제안 STALE |

속성 기반 테스트는 jqwik으로 입고·이동·할당·출고·조정·역분개를 무작위로 섞은 시퀀스를 만들고, 매 단계마다 [정합 검증 배치](06-events-reconciliation.md#정합-검증-배치)의 쿼리가 0건인지 확인한다. 테스트 결과(스레드 수, 반복 횟수, 실패 0건)를 README에 표로 남기면 정합성 우선이라는 주장을 증거로 보여줄 수 있다.

## 구현 순서

| 단계 | 기간 | 내용 | 완료 기준 |
|---|---|---|---|
| 1 | 2주 | 스키마, 포스팅 서비스(입고·이동·조정·역분개), 멱등성 | 멱등성·트리거·역분개 테스트 통과 |
| 2 | 2주 | 할당·출고·반품, 실사 세션, 판매 가능 수량 뷰, 센터 간 이동 | 동시 할당·데드락·실사 경합·정정 롤백 테스트 통과 |
| 3 | 1~2주 | 아웃박스 릴레이, 정합 검증 배치, `inventory_issue`(+ `count_session_id`·처리 이력 컬럼, `(status, detected_at)` 인덱스) | 잔액을 일부러 틀어놓으면 배치가 최초 불일치 거래를 찾아낸다 |
| 4 | 2~3주 | 조회 뷰와 MCP 도구, 불일치 원인 분석, 제안·승인(+ `action_proposal (status, created_at)` 인덱스) | 에이전트 재시도·동시 승인에도 실행 1회, STALE 처리 동작 |

3단계에서 `inventory_issue`에 더할 컬럼은 검증에서 나온 것이다. 실사 차이 이슈를 다시 찾으려면 `detail->>'countSessionId'`로 JSONB 문자열을 비교해야 했고, 상태가 세 단계인데 누가 언제 처리했는지가 남지 않았다. 이 테이블을 실제로 쓰기 시작하는 단계에 함께 넣는다.

4단계에서는 `inventory_ledger_entry.occurred_at` 비정규화를 결정한다. 수요 예측이 "`SHIPMENT` 원장의 일별 집계, `occurred_at` 기준"인데 이 컬럼이 거래 헤더에만 있어 가장 큰 테이블에 매번 조인이 붙는다. 다만 비정규화는 되돌리기 어려우므로 실제 집계 쿼리를 측정한 뒤에 판단한다.

측정은 끝났다. PostgreSQL 16, 원장 300만 행 · 거래 150만 행 · SKU 2000 규모에서 같은 집계 쿼리(90일 창)를 돌려보면 현재 스키마(조인) 700ms(워밍) / `occurred_at`만 비정규화 6697ms / `occurred_at`·`txn_type` 둘 다 비정규화 823ms이고, 원장 크기는 621MB → 1244MB로 두 배가 된다. **병목은 조인이 아니라 원장 전체 스캔이다** — 네 변형 모두 실행 계획이 `Parallel Seq Scan on inventory_ledger_entry`였고, 거래 헤더에 `inventory_txn (txn_type, occurred_at)` 인덱스를 얹어도(926ms) 인덱스 없는 현재 스키마(700ms)와 차이가 없었다. 조인을 없애도 스캔 비용은 그대로 남는다는 뜻이다.

로드맵에 적어 둔 형태(`occurred_at`만 비정규화)가 오히려 가장 나쁘다. `txn_type` 필터가 여전히 거래 헤더에 남아 조인이 사라지지 않는데, 원장만 두 배로 커져 스캔 비용만 늘어난다. 부담이 훨씬 작을 7일 창에서도 부분 인덱스를 붙인 완전 비정규화(716ms)가 현재 스키마(649ms)에 졌다.

**결론: 비정규화하지 않는다.** 같은 사실을 원장과 파생 컬럼 두 곳에 저장하면 둘이 어긋날 수 있고, 그것을 막을 불변식이 하나 더 필요해지는데 얻는 것은 없다. 집계 지연이 실제로 문제가 되면 비정규화가 아니라 일별 롤업 테이블이 맞는 답이다 — 원장이 append-only라 이미 집계된 구간은 바뀌지 않으므로 증분 갱신이 자연스럽고, 원장 스키마 자체는 건드리지 않는다.

1~3단계만으로도 정합성을 DB 수준에서 증명하는 재고 코어라는 백엔드 포트폴리오가 되고, 4단계가 그 위에 AI 역량을 얹는 부분이다.

## 부록. MySQL 8을 쓴다면

CHECK 제약은 8.0.16부터 실제로 강제되고, 생성 컬럼과 `SKIP LOCKED`도 지원된다. 다만 지연 제약 트리거가 없어서 I3(거래 합계 0)는 애플리케이션 검증과 배치로만 지켜야 한다. 부분 인덱스도 없으므로 `WHERE status = 'ACTIVE'` 조건의 인덱스는 일반 인덱스로 바꾸고, 대기 중 제안의 중복 방지는 PENDING일 때만 값을 갖는 생성 컬럼에 UNIQUE를 거는 방식으로 대신한다. 기본 격리 수준인 REPEATABLE READ에서는 갭 락 때문에 없는 행을 삽입하는 경합에서 데드락 양상이 달라지므로, 잠금 규칙은 같더라도 동시성 테스트는 MySQL에서 다시 돌려야 한다.

가장 널리 퍼져 있는 의존은 `INSERT ... ON CONFLICT DO NOTHING`이다. 멱등 키 선점과 잔액 행 선생성에 쓰이며, 애플리케이션 SQL 13개 문장 중 2곳, 검증 하네스에 6곳 있다. MySQL에는 이 문법이 없고 대안이 둘인데 주의할 점이 다르다. **`INSERT IGNORE`는 쓰지 않는다.** 중복 키뿐 아니라 데이터 절삭이나 외래키 위반까지 모든 오류를 경고로 강등해버려서, "DB가 틀린 데이터를 막는다"는 이 설계의 전제와 정반대로 간다. `INSERT ... ON DUPLICATE KEY UPDATE idem_key = idem_key` 같은 무의미 갱신 쪽이 맞다. 다만 영향 행 수 의미가 달라서(삽입 1 / 갱신 2 / 값이 그대로면 0) "새로 선점했는가"를 판정하는 코드는 그대로 옮길 수 없다.

`RETURNING`도 MySQL에 없다. 거래 헤더의 생성된 id는 JDBC `getGeneratedKeys()`로 대신할 수 있지만, 잔액 적용의 `UPDATE ... WHERE (가용 조건) RETURNING on_hand_qty`는 대체가 번거롭다. 한 왕복으로 끝나던 상대 갱신·가용 검사·적용 후 값 읽기가 UPDATE → 영향 행 수 확인 → 잠금 아래 SELECT 세 단계로 흩어지고, 원장의 `on_hand_after`를 채우는 경로가 길어진다.

**표준 SQL의 `MERGE`로 바꾸는 것은 답이 아니다.** PostgreSQL에 그대로 남아 있더라도 마찬가지다. `ON CONFLICT`에는 동시 삽입을 위한 특별한 처리가 있어 커밋되지 않은 충돌 행을 만나면 기다렸다가 판정하지만, `MERGE`에는 그것이 없어 동시 삽입 경합에서 유니크 위반으로 실패할 수 있다. 같은 멱등 키로 동시에 들어온 요청이 하나만 통과하는 보장(테스트 전략의 동시성 시나리오)이 깨지므로, 표준 준수를 위해 멱등성을 깎는 교환이 된다.
