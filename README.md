# Zerosum

재고관리 코어. **정합성은 DB 수준에서 강제하고, AI 기능은 그 위에 얹는다.**

이름은 복식부기에서 왔다. 모든 재고 이동은 (SKU, 로트)별 수량 합이 0이다 — 어딘가에서 빠지면 반드시 어딘가로 들어간다. 이 합이 0이 아닌 원장은 애플리케이션이 막는 것이 아니라 커밋 시점에 DB 트리거가 거절한다.

```
                         ┌──────────────────────────────────────┐
  OMS · 현장 앱 ────────▶│  포스팅 서비스 (유일한 쓰기 경로)      │
                         │  멱등 키 선점 → 잠금 → 잔액 → 원장     │──▶ outbox
  AI 에이전트 ──읽기──▶  │                                      │
       │                 └──────────────────────────────────────┘
       │                                  ▲
       └─ 제안(PENDING) ─── 사람이 승인 ──┘   AI는 제안까지만. 실행은 사람이.
```

## 무엇을 증명하려는 저장소인가

재고 시스템에서 "재고가 안 맞는다"는 대부분 코드의 버그가 아니라 **동시성과 부분 실패**에서 온다. 두 주문이 같은 마지막 하나를 가져가고, 재시도가 같은 출고를 두 번 태우고, 실사 중에 출고가 끼어든다.

이 저장소는 그것을 규율이 아니라 **구조로** 막는다. 그리고 막혔다는 것을 증거로 보인다.

| 증거 | 수치 |
|---|---|
| 테스트 | **348건 PASS** (core 252 / web 51 / 프론트 42 / mcp-server 3), 실패·에러 0 |
| 스키마 하네스 (PL/pgSQL) | **191건 PASS** |
| 속성 기반 시퀀스 | **4,400 연산**을 무작위로 섞어 실행, 매 단계 정합 검증 0건 |
| 테스트 DB | Testcontainers PostgreSQL 16 (H2 아님 — 행 잠금과 지연 제약이 달라 증거가 되지 못한다) |

## 정합성을 어떻게 강제하는가

불변식 11개(I1~I11)를 **3중**으로 건다. 앱 검사는 좋은 오류 메시지를 위해, DB 제약은 진짜 방어를 위해, 배치 검증은 그래도 새는 것을 찾기 위해.

| | 예 |
|---|---|
| 앱 검사 | 차감 전 가용 확인, 커맨드 합계 0 검증 |
| **DB 제약** | `CHECK (on_hand_qty >= 0)`, `CHECK (allocated_qty <= on_hand_qty)`, 지연 제약 트리거(합계 0), 부분 유니크 인덱스(로케이션당 실사 1개), 원장 `UPDATE`·`DELETE` 권한 없음 |
| 정합 검증 배치 | ① 잔액 투영 ② 할당 ③ 원장 체인 ④ 가상 로케이션 잔액 ⑤ 실사 표시 |

전문은 [설계 원칙과 불변식](docs/01-principles.md).

PostgreSQL 의존은 이식성을 위해 줄이지 않고 **의도적으로 받아들였다.** 지연 제약 트리거, 부분 유니크 인덱스, `INSERT ... ON CONFLICT`가 모두 표준 SQL로 표현되지 않는데, 표준 문법으로 바꾸면 지켜지던 불변식이 규약으로 내려앉기 때문이다. 대신 벤더 의존을 리포지토리 계층에 가뒀다.

## AI는 어디까지 할 수 있는가

권한을 코드가 아니라 **DB 롤로** 가른다. 다섯 개다 — `migrator`, `app_admin`, `app_rw`, `ai_ro`, `ai_proposer`.

AI가 쓸 수 있는 것은 두 곳뿐이고, 그 경계는 컬럼 단위 권한이 정한다:

```sql
GRANT SELECT (id, status) ON inventory_issue TO ai_proposer;
GRANT UPDATE (ai_analysis) ON inventory_issue TO ai_proposer;
```

이 두 줄 때문에 AI는 이슈에 원인 분석을 적을 수는 있어도 **상태를 바꿀 수 없고**, 누가 언제 확인했는지(`acked_by`)를 **읽지도 못한다.** 프롬프트로 부탁하는 것이 아니라 SQL 문법 수준에서 막힌다 — 시도하면 `42501`이다.

`inventory_txn.actor_type`에 `'AI'`는 없다. 제안이 실행되면 그 거래의 행위자는 승인한 사람이다.

전체 사슬:

```
정합 검증 배치가 불일치를 탐지  →  OPEN 이슈
  →  AI가 ai_analysis에 원인 후보를 기록          (MCP · ai_proposer)
  →  AI가 action_proposal로 복구를 제안            (MCP · 창고 범위 강제)
  →  사람이 근거 대조를 보고 승인                  (웹 · SUPERVISOR)
  →  actor_type=USER 로 실행, 멱등 키 proposal:{id}
  →  그 거래 id로 이슈 RESOLVED
```

제안은 **승인 시점에 근거를 다시 검증한다.** 제안을 만들 때 본 잔액을 `basis_snapshot`에 남겨두고, 승인할 때 잠금 아래에서 다시 비교해 그 사이 재고가 변했으면 실행하지 않고 `STALE`로 끝낸다. 자세히는 [AI 연결 지점](docs/07-ai-integration.md).

## 증거

### 동시성 시나리오

경합하는 쓰기를 실제 스레드로 부딪혀 본다. 아래는 구현된 시나리오의 실제 규모다.

| 시나리오 | 규모 | 기대 결과 |
|---|---|---|
| 같은 잔액 행을 동시에 차감 | 10스레드, 가용 20을 5씩 | 정확히 4건 성공, 잔량 0 |
| 같은 SKU를 동시에 할당 | 10스레드, 가용 20을 5씩 | 정확히 4건 성공, 초과 할당 0 |
| 같은 멱등 키로 출고를 동시에 | 10스레드 | 거래 1건, 10개 모두 같은 거래 id를 받고 할당 소진도 1회 |
| 같은 제안을 동시에 승인 | 5스레드 | EXECUTED 1회 |
| 실사 시작과 출고가 동시에 경합 | 2스레드 | 출고는 실사 시작 전에 커밋되거나 거절, `system_qty`가 원장 합계와 일치 |
| 제안 후 재고가 크게 변한 뒤 승인 | — | 원장 기록 없음, 제안 STALE |

가장 큰 동시 부하는 아래 속성 테스트의 P2(8스레드 × 50연산)다. 설계 단계에서 잡아둔 시나리오 목록은 [테스트 전략](docs/08-testing-roadmap.md#테스트-전략)에 있고, 그 중 규모를 크게 잡은 항목(200스레드·1,000회)은 아직 그 규모로 돌리지 않는다.

### 속성 기반 시퀀스 테스트

시나리오 테스트가 검사하는 것은 **내가 떠올린 경합**뿐이다. 그래서 여섯 연산(입고·이동·조정·할당·출고·역분개)을 무작위로 섞은 시퀀스를 만들어 돌린다.
→ [`InventorySequencePropertyTest`](core/src/test/java/com/zerosum/inventory/property/InventorySequencePropertyTest.java)

오라클이 둘이다. 하나로는 약하다 — 잔액과 원장이 **같은 방향으로 함께 틀리면** 정합 검증은 통과한다.

| 오라클 | 무엇을 본다 |
|---|---|
| ① 불변식 | 정합 검증 ①~⑤가 0건인가 (DB 내부 정합) |
| ② 모델 | 테스트가 발행한 커맨드로부터 **독립 계산한** 기대 재고 == 실제 `stock_balance` (커맨드 → 상태 정합) |

②는 롤백이 완전한지도 같이 본다. 거절된 연산은 모델을 건드리지 않으므로, DB에 흔적이 남으면 불일치로 잡힌다.

**P1 — 단일 스레드, 100 시퀀스 × 40 연산, 매 연산마다 ①②** (고정 시드 `20260915`)

| 연산 | 시도 | 성공 |
|---|---:|---:|
| RECEIPT | 809 | 809 |
| MOVE | 748 | 490 |
| ADJUSTMENT | 728 | 458 |
| ALLOCATE | 759 | 428 |
| SHIPMENT | 312 | 312 |
| REVERSAL | 644 | 478 |
| **합계** | **4,000** | **2,975 (74.4%)** |

거절 1,025건은 전부 `INSUFFICIENT_STOCK`(660) · `NO_STOCK`(365) — 재고가 없어서 거절된 정상 경로다.

**P2 — 8스레드 × 50 연산, 끝에서 정합 검증 + 보존 오라클**: 400 시도 중 331 성공(82.8%). 인터리빙 때문에 같은 시드에서도 실행마다 수치가 달라진다.

**거절을 삼키지 않는다.** 생성기는 합법적으로 실패하는 연산을 만든다. 그걸 전부 `catch (Exception e) {}` 하면 테스트는 아무것도 검사하지 않게 된다. 그래서 거절은 코드 화이트리스트(`INSUFFICIENT_STOCK`, `NO_STOCK`, `ORPHAN_CONSUME`, `ALLOC_NOT_ACTIVE`, `COUNT_IN_PROGRESS`, `NOT_ZERO_SUM`, `REASON_REQUIRED`, `UNKNOWN_CODE`)로만 허용하고, 그 밖의 예외 — 데드락, NPE, 제약 위반 누출 — 는 그대로 실패다.

**생성기가 실제로 일하는지도 검사한다.** 전체 성공률 40% 이상, 여섯 연산이 각각 25% 이상 성공해야 통과한다. 이 가드는 실제로 한 번 일했다 — 처음엔 MOVE가 출발지를 눈감고 골라 성공률 11%에 머물렀고(시퀀스 40연산당 성사된 이동 1.2개꼴), 그 상태로도 모든 단언은 통과했다. 생성기를 고치니 65%가 됐다.

시드는 고정이라 CI가 매번 같은 시퀀스를 돈다. 다른 시드로 탐색하려면:

```bash
./gradlew :core:test --tests "*InventorySequencePropertyTest*" -Dzerosum.property.seed=77777
```

### 프론트엔드

화면이 서버 규칙을 다시 계산하는 곳은 없다 — FEFO도, 실사 허용오차도, 근거 유효성도 서버 응답에서 온다. 그래서 프론트 테스트가 볼 것은 **클라이언트 상태뿐**이다: 인증 전이, 캐시 무효화, 자격 증명 보관.

응답 형태가 어긋나는 문제는 백엔드 쪽 테스트가 지킨다(`AllocationLinesTest`, `StockVisibilityTest`). 그 종류는 프론트에서 mock으로는 잡을 수 없다 — 내가 쓴 mock으로 내 가정을 확인할 뿐이기 때문이다. 그래서 E2E는 두지 않았다.

Vitest + Testing Library + MSW로 42건 — 화면 일곱 중 여섯을 덮는다(원장 화면은 읽기 전용이라 뺐다). 각 테스트는 자기가 잡겠다는 버그를 되살려 실제로 빨간불이 되는지 확인했다.

```bash
cd frontend && npm run test
```

### 스키마 하네스

DDL만 바꿨을 때 Java 컴파일 없이 몇 초 만에 전부 다시 돌려보는 PL/pgSQL 하네스. 유스케이스 **191건**.

```bash
bash db/run.sh
```

## 구조

```
:core          정합성 코어. 웹 의존 없음. 원장·잔액·할당·실사·제안·정합 검증
:web           사람의 진입점. JSON API + 빌드된 SPA 서빙
:mcp-server    AI의 진입점. MCP STDIO 도구 6개
frontend/      React 19 + Vite. 화면 일곱 — 재고·원장·입고·출고·실사·제안·이슈
db/            마이그레이션(Flyway) · 롤 · 시드 · PL/pgSQL 하네스
docs/          설계 문서 9편
```

모듈 의존은 단방향이다. 그리고 **이 저장소에는 JSON을 파싱하는 Java 코드가 없다** — Jackson `import` 0건, `ObjectMapper` 0건이다(클래스패스에는 Flyway·Hibernate가 전이 의존으로 올려둘 뿐이다). JSON은 전부 PostgreSQL JSONB 연산자가 다룬다. 제안 payload의 정규화도 SQL의 `jsonb_build_object`로 한다 — 같은 내용을 다르게 적은 재시도가 DB 안에서 한 모양으로 접힌다.

Java 21 · Spring Boot 4.1.1 · PostgreSQL 16 · Gradle 9.7.1 · Spring AI 1.1.0 · React 19.3 · TypeScript 7.0

## 범위 밖

피킹 웨이브, 패킹, 운송장, 부분 출고, 주문 관리는 다루지 않는다 — 외부 시스템이 이 코어에 커맨드를 보낸다고 가정한다.

**금액도 범위 밖이다.** 이 코어는 수량과 위치만 책임진다. 원가 계산과 재고자산 평가는 `StockPosted` 이벤트와 원장 id를 받아 ERP가 한다.

명시적으로 미뤄둔 것: `RESOLVE_COUNT`·`TRANSFER` 제안 타입(`MOVE`·`ADJUSTMENT`로 사슬이 이미 증명된다), 발주 데이터 기반 근거(`po_line`).
